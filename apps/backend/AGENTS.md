# Backend code generation rules

Read this file before changing `apps/backend`. Root monorepo, quality, and Git rules live in `/AGENTS.md`. This file is the source of truth for backend ownership and dependency direction. Use `emails` as the use-case, repository, and controller reference for new features, and `health` as the smallest feature.

## Status and map

| Area                     | Owns                                                                                                                                           | Current reference                                          |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `src/api/`               | HTTP application: bootstrap, composition, controllers, HTTP request/response DTOs, validation, authentication, and HTTP error/response mapping | `api/api.module.ts`, `api/endpoints/emails/`, `api/core/`  |
| `src/worker/`            | Queue application: bootstrap, job consumers, queue payload validation, and job result/error mapping                                            | `worker/main.ts`, `worker/queues/*/*-job.handler.ts`       |
| `src/modules/<feature>/` | Business capabilities: use cases, business errors, feature-owned repository ports and adapters, and Nest feature wiring                        | `modules/emails/` and `modules/health/` (smallest example) |
| `src/common/`            | Non-domain infrastructure reusable by the API and worker, such as database connection setup and technical error bases                          | `common/database/`, `common/errors/`                       |

`api/endpoints/<feature>/` always owns HTTP controllers and HTTP DTOs. `modules/<feature>/` owns the corresponding business behavior and errors. There are no feature-specific HTTP controllers or DTOs in `modules/`. A queue consumer belongs to `worker/`, not the feature module.

## Dependency direction

```text
api/ ──────┐
           ├──> modules/ ──> common/
worker/ ───┘       │
   │               └──> another module's public use case
   └─────────────────────> common/
api/ ────────────────────> common/
```

- `api/` and `worker/` may call use cases in `modules/`, import their public input/result/error types, and use infrastructure in `common/`. They do not import each other.
- `modules/` may use `common/`, including database infrastructure, but never imports `api/` or `worker/`. Business rules and errors stay in the owning feature.
- One feature may call another feature's **public use case** and import the types in that use case's interface. Its repository ports, adapters, internal helpers, and Nest providers other than public use cases are private. Nest module imports/exports may wire public use cases for injection. Keep feature dependencies acyclic.
- `common/` is reusable infrastructure, not a home for business rules. It imports neither an application (`api/`, `worker/`) nor a feature module.
- Import local files directly; use the `@/` alias across directories and `.js` extensions where NodeNext resolution requires them.

These ownership and direction rules are currently **conventions**: the old dependency-cruiser configuration was removed during the refactor, and no replacement boundary check exists yet. Do not describe them as machine-enforced or weaken lint rules to accommodate a violation.

`modules/jobs/job.service.ts` owns public status reconciliation on reads, interrupted-attempt activity, attempt lifecycle transitions, and processing-job recovery. Its repository port exposes focused persistence methods such as `getJob`, `setJobStatus`, `addJobLog`, and `cancelJob`, and an atomic `writeJobTransition` for status, result, and activity writes; Drizzle queries remain in `job.repository.ts`. Cancellation keeps the queue and application updates in one repository transaction with queue-row locking, so a concurrent worker pickup cannot race it. This boundary is a convention; TypeScript checks the port and job tests check behavior, but no dependency rule enforces service placement.

Read side and retry (`ListJobsUseCase`, `GetJobStatsUseCase`, `RetryJobUseCase`, routes in `api/endpoints/jobs/jobs.controller.ts`: `GET /api/jobs`, `GET /api/jobs/stats` registered before `GET /api/jobs/:id`, `POST /api/jobs/:id/retry`): `listJobs`, `getJob`, and `countJobsByStatus` in `job.repository.ts` compute the **effective status** in SQL (a `scheduled` row whose pg-boss `start_after`, falling back to `start_at`, has passed is `pending`; reads never write it), plus `attempts` (count of `started` events), `completedAt` (latest terminal event while terminal), and `lastErrorCategory` from `job_activity`. `JobService.get` re-reads the row after its reconciliation writes so those figures are current. `retryJob` runs in one transaction that locks the `jobs` row and the pg-boss row, requires both to be `failed`, calls pg-boss `retry` (state `retry`, `retry_limit + 1`, `retry_count` kept), pulls `start_after` to now, raises `max_attempts` by one, sets `pending`, and appends `retried:<n>` (n is the new attempt number, `retry_count + 2`); `JobService.retry` reconciles the status first. `failed` activity events are keyed `failed:<attempt>` so a retried job can fail terminally again. Reference: `modules/jobs/job.repository.ts`, `api/endpoints/jobs/jobs-management.e2e-spec.ts` (filters, search, pagination, effective status, stats, retry, racing retries, per-job limits). Conventions checked by unit and integration tests.

`GET /api/health` (`api/endpoints/health/health.controller.ts`, no auth) is the HTTP read over `CheckHealthUseCase` in `modules/health/`. The use case pings the database and queue through the `HealthChecks` port (`ports/health-checks.ts`, Drizzle/pg-boss adapter `health-checks.ts`: `SELECT 1` and `getQueue('email')`), each bounded by a 2 second timeout, and takes the counts from the public `CountJobsByStatusUseCase` in `modules/jobs/` (the same `countJobsByStatus` SQL as `GetJobStatsUseCase`, no duplicated SQL). It is used instead of `GetJobStatsUseCase` because that one also calls pg-boss (`isHealthy`), so a hung queue would make the database look down. A failed or timed-out check becomes `down` and its error text is dropped; counts are all zeros when the database is down (or the count query fails, which also marks the database down). The report is `{ status: 'ok' | 'down', checks: { database, queue }, counts }`. The controller returns 200 for `ok` and throws `ServiceUnavailableException` (`code: 'SERVICE_UNAVAILABLE'`) for `down`, putting the report in `error.details` so the client sees the failed check. There is no worker tracking: pg-boss has no worker registry. Reference: `use-case/check-health.use-case.spec.ts`, `health.controller.spec.ts`, `health.e2e-spec.ts`. Conventions checked by unit and integration tests.

`GET /api/aircraft-transit-reports/:id` (`api/endpoints/aircraft-transit-reports/`) is the HTTP read over `GetAircraftTransitReportUseCase`; it returns the airports, aircraft, times, distance, duration, and waypoints, and maps `AircraftTransitReportNotFoundError` to 404 through `toHttpException`. The aircraft report job result is `{ reportId }`.

Queue applications use `common/queue/QueueModule` for pg-boss connection lifecycle. Only the worker imports `worker/core/pg-boss/JobHandlerRegistry`, which discovers `@JobHandler` providers and registers consumers; the API imports the queue module to publish without starting a consumer. `modules/jobs/` owns job state, submission idempotency, and append-only activity; both entry points call its public use cases. This separation prevents HTTP handlers from executing delivery work and keeps queue settlement decisions in `worker/`. References: `common/queue/`, `modules/jobs/`, `worker/`, and `api/endpoints/jobs/`. The folder direction is a convention; TypeScript and integration tests check the wiring.

Queue startup is read-only after `pnpm run setup`: `scripts/migrate-queue.mjs` owns pg-boss schema and queue DDL for every queue in `QUEUES` (`email`, `webhook`, `aircraft-report`), while `common/queue/queue.service.ts` starts with migrations disabled and verifies each queue in `QUEUES`. The script cannot import TypeScript, so it repeats the list; `queue.service.spec.ts` checks the two match. Add a queue by extending `QUEUES` and the script list, then registering a `@JobHandler(<queue>)` provider in `worker.module.ts`. Attach an `error` listener before `start()` and log only a safe infrastructure category so pg-boss failures cannot become unhandled process errors or expose query parameters. `worker/modules/activity-logs/job-recovery.service.ts` reconciles processing rows at startup and every five seconds; `recordStart` backfills missed attempt events before the next start. This preserves activity even when no GET occurs between retries. The queue listener has a unit check, and recovery has database integration checks; startup order is verified against a disposable database.

## Use cases and feature ownership

**Pattern for new work:** create one public use-case class per user or job action, named `<Action>UseCase`, with one `execute(input)` method. The input and output are plain business/application types, not HTTP DTOs or queue messages. Return a `Result` for expected failures. For example, `CreateOrderUseCase.execute(...)` belongs in `modules/order/use-case/`; an HTTP controller and a queue consumer may both invoke it.

- Keep the action's business sequence in its use case. Controllers adapt HTTP input/output; consumers adapt queue input/output. Neither application duplicates business decisions.
- A feature that persists data declares its repository port and owns its Drizzle adapter **inside that feature**. `common/database/` supplies the reusable connection and transaction machinery, not feature queries.
- Feature use cases may use Nest injection and scoped `PinoLogger`, as `CheckHealthUseCase` and `SendEmailUseCase` do. Inject dependencies rather than creating database clients inside a use case.
- A use case may call another feature's public use case when one business action requires it. Wire the public class through Nest modules and keep the dependency one-way.
- Put every feature use-case class in `src/modules/<feature>/use-case/` so application actions have a predictable location. Reference: `modules/emails/use-case/send-email.use-case.ts` and `modules/emails/use-case/list-sent-emails.use-case.ts`. This is a convention; no machine check enforces it yet.
- Add other folders inside a feature only when needed. Ports live in `src/modules/<feature>/ports/`; repository adapters use `<entity>.repository.ts` at the feature root (the storage technology stays out of the filename); other adapters stay beside the feature they serve; tests sit next to their source files.

The email feature implements this pattern: `modules/emails/use-case/send-email.use-case.ts` and `modules/emails/use-case/list-sent-emails.use-case.ts` own actions, `ports/email.repository.ts` declares the repository port, and `email.repository.ts` owns persistence and ID cursor queries. Declare each port as an interface with its exported symbol injection token in the same `ports/` file. Use type-only interface imports, explicit `@Inject(TOKEN)` in use-case constructors, and `{ provide: TOKEN, useClass: Adapter }` in feature modules; adapters implement the interface. This keeps the contract independent of inheritance while supplying Nest with a runtime injection identity. References: `modules/emails/ports/email.repository.ts`, `ports/email-client.ts`, `use-case/send-email.use-case.ts`, and `emails.module.ts`. This pattern is a convention; TypeScript checks interface implementation, but no machine check enforces folder placement or token colocation. Adapters stay private to the feature module. `ports/email-client.ts` keeps delivery replaceable, with `mock-email.client.ts` waiting 1–3 seconds and then failing with `EmailDeliveryFailedError` (`email.errors.ts`) with 10% probability (`randomInt(0, 10) === 0`), following the webhook mock. The client returns `Result<{ messageId }, EmailDeliveryFailedError>`, `SendEmailUseCase` preserves the error and persists nothing on failure (so a same-key retry is a fresh attempt), the emails controller maps it to 502 through `to-http-exception.ts`, and `worker/queues/email/email-job.handler.ts` records it as a retryable `attempt_failed` with category `delivery_failed`, not a defect. The error has no email content. Conventions; unit specs cover each seam. These ownership rules are conventions, not machine-enforced. `worker/queues/email/email-job.handler.ts` is the queue consumer reference.

The email list uses descending `eml_<ULID>` IDs, an exclusive ID cursor, and one extra row to determine `nextCursor`. HTTP page limits are 1–100 (default 20). `api/endpoints/emails/` owns validation and date serialization. The send action persists only after successful delivery (an expected delivery failure returns the error and stores nothing); delivery and insertion cannot share a database transaction, so a persistence failure after delivery may require reconciliation when a real provider is introduced. Email content is not logged by feature code. The repository replaces database query exceptions with generic technical errors because Drizzle error messages can include email parameters and the HTTP filter logs unexpected errors.

Webhook calls require a job ID (a `jobs` foreign key) and a delivery key, and append one database record for each completed delivery attempt, including expected failures, before returning the delivery `Result` (`{ callId, receipt }` on success). This preserves retry history and makes either outcome discoverable by job ID. A partial unique index allows one succeeded record per job: a repeated success after a worker crash returns the stored record's ID instead of inserting. `modules/webhooks/use-case/call-webhook.use-case.ts` owns this sequence; `ports/webhook.repository.ts` and `webhook.repository.ts` own persistence. `use-case/list-webhook-calls.use-case.ts` exposes attempts by job ID in descending recorded time, with descending ID as a tie breaker, returning the stable success receipt or stored error name/message. Only these public use cases are exported through `WebhooksModule`. URL and payload are not stored; database exceptions are replaced with generic technical errors to avoid parameter leakage. Delivery and persistence cannot share a transaction: unexpected storage failure throws and may require reconciliation after a real delivery. Ownership and sequencing are conventions; the database enforces record ID and outcome consistency and indexes job lookup.

The mock webhook client fails with one-in-three probability (`randomInt(0, 3) === 0`) for every URL; URL text never forces failure. This keeps the simulation independent of user input. Reference: `modules/webhooks/mock-webhook.client.ts`; its unit spec checks both outcomes for a `/503` URL. This rule is covered by tests, not lint.

Aircraft transit reports live in `modules/aircraft-transits/`. `use-case/validate-aircraft-transit-request.use-case.ts` (submission validation, including the past-departure check, saves nothing) and `use-case/generate-aircraft-transit-report.use-case.ts` (no past check, so queued or retried jobs do not fail as time passes) share the private `use-case/validate-transit-request.ts`; `CreateAircraftReportJobUseCase` (in `modules/jobs/`) calls Validate at submission and `worker/queues/aircraft-report/aircraft-report-job.handler.ts` calls Generate. Generate takes a `jobId`; `aircraft_transit_reports.job_id` is unique and `saveReport` returns the report already stored for a repeated job, so a retried job yields one report. `use-case/get-aircraft-transit-report.use-case.ts`, `list-airports.use-case.ts`, and `list-aircraft.use-case.ts` complete the public set, and `AircraftTransitsModule` exports only those. `transit-path.ts` is a pure Turf-based path builder. The `Clock` (`ports/clock.ts`, `system.clock.ts`) and `SimulationDelay` (`ports/simulation-delay.ts`, `random-simulation-delay.ts`, 1-3 seconds) ports keep time and simulated work replaceable; unit specs use fakes from `testing/`. `aircraft-transit.repository.ts` is the Drizzle adapter over the seeded `airports` and `aircraft` tables and `aircraft_transit_reports`, verified by `aircraft-transit.repository.e2e-spec.ts` (`pnpm --filter backend test:integration` on a migrated, seeded database). Reference data is exposed by `GET /api/airports` and `GET /api/aircraft` (`api/endpoints/airports/`, `api/endpoints/aircraft/`); reports are created only through `POST /api/jobs/aircraft-report`. Conventions, not machine-enforced.

## Results and errors

- Replaceable delivery clients return `Result` for expected delivery failures, and their use cases preserve that result so application entry points can decide retry behavior. Reference: `modules/webhooks/ports/webhook-client.ts`, `mock-webhook.client.ts`, and `use-case/call-webhook.use-case.ts`. The webhook mock accepts a URL, JSON payload, and delivery key without network access, waits 1–2 seconds, and returns `WebhookDeliveryFailedError` with one-in-three probability (`randomInt(0, 3) === 0`). Demo failure: the email mock always fails a recipient ending in `@bounce.test` (case-insensitive), so the UI can demo retries on demand; the recipient does not appear in errors or logs. Its success receipt always has `{ requestId, status: 'delivered', body: { accepted: true, value } }`; the request ID is `mock_` plus the SHA-256 of the delivery key and `value` is an integer from 0 through 999,999 derived from the same digest, so a repeated key returns the same receipt. Neither payload nor URL appears in the error. This keeps expected delivery failures distinct from defects; the pattern and probability are conventions, not machine-enforced.
- A use case returns `neverthrow` `Result<Success, FeatureError>` for expected business failures. Define each expected error as a class in the owning feature (see `modules/emails/email.errors.ts`). Unexpected defects may throw and are handled by the application entry point.
- The HTTP controller maps a feature error to an HTTP exception at `api/endpoints/<feature>/`; `api/core/errors/to-http-exception.ts` is the current mapping helper. The API's global envelope lives in `api/core/response-envelope/`.
- A worker consumer maps the same feature error to the job's retry, failure, or completion behavior in `worker/`. Queue semantics belong to the worker, not the use case.
- `EnvelopeFilter` logs every 5xx with its full `cause` chain (up to 5 levels, plus `code`/`detail` when present). Why: Drizzle wraps the Postgres error in `cause`, which `stack` omits, so the log otherwise shows only the SQL. `detail` can contain key values, which is why repositories that handle user content wrap DB errors in generic ones. Reference: `api/core/response-envelope/envelope.filter.ts`. Convention; no test enforces it.
- Do not put HTTP status codes, Nest HTTP exceptions, or queue retry decisions in use-case results.

## HTTP DTOs and validation

- Define HTTP request and response schemas with Zod and classes with `nestjs-zod` in `api/endpoints/<feature>/dtos/`. See `api/endpoints/emails/dtos/`.
- Type decorated controller parameters with the **runtime DTO class**. Nest needs that class in decorator metadata for the global `ZodValidationPipe` in `api/core/validation/validation.module.ts`; a type-only import erases it.
- The controller passes plain values to a use case, then creates a response DTO from its result. Zod validates transport shape and format; the feature use case decides business rules.
- HTTP validation failures are mapped by `api/core/response-envelope/` to the API error envelope. Worker payload validation belongs in `worker/`; `worker/queues/email/email-job.handler.ts` validates before delivery.

## Swagger documentation

- Document every HTTP endpoint with tags, an operation summary, validated request/query schemas, and success/error envelopes. Use `api/core/swagger/api-envelope-response.ts` with the response Zod DTO’s `.Output` schema so Swagger describes the global envelope rather than the controller’s `Result` wrapper. Reference: `api/endpoints/emails/emails.controller.ts` and `api/endpoints/health/health.controller.ts`. Coverage is a convention; no machine check enforces it yet.
- Configure Swagger in `api/core/swagger/swagger.config.ts`, called by `api/main.ts` after the global prefix is set. Run `cleanupOpenApiDoc` after `SwaggerModule.createDocument` for correct Zod schemas. Swagger UI is `/api/docs` and its JSON document is `/api/docs-json`.

## Configuration

`pnpm dev` (`pnpm --filter backend dev`) runs the API and two workers through `concurrently`. The API's `nest start --watch` owns and rebuilds `dist/`; each worker is `node --watch` on `dist/worker/main.js` after `wait-on`, because parallel `nest start` watchers would each delete the shared output directory. Two workers exercise concurrent job consumption and pg-boss locking; `worker:dev` alone starts one more. After `pnpm --filter backend build`, use `pnpm --filter backend start` and `pnpm --filter backend worker:start`. Both use the root `DATABASE_URL`; `pnpm run setup` runs backend `queue:migrate` after Drizzle migrations to create or upgrade pg-boss and every queue. API and worker start pg-boss with migrations disabled and refuse a missing queue. `POST /api/jobs/email`, `/webhook`, and `/aircraft-report` enqueue without a worker, and the worker closes its queue connection on shutdown. The same `DATABASE_URL` must point to a database prepared by `pnpm setup`. Reference: `api/api.module.ts`, `worker/worker.module.ts`, `common/queue/queue.service.ts`; startup is checked by the jobs integration suite, while deployment separation remains an operational convention.

Example: `POST /api/jobs/email` with JSON `{ "idempotencyKey": "11111111-1111-4111-8111-111111111111", "type": "schedule", "priority": 5, "startAt": "2030-01-01T12:00:00Z", "payload": { "recipient": "person@example.com", "subject": "Welcome", "body": "Hello" } }`. The response is HTTP 202 with `id` and `startAt`; use `GET /api/jobs/:id` for status and activity or `DELETE /api/jobs/:id` before processing to cancel. `POST /api/jobs/webhook` takes the same envelope with `payload: { url, payload }` (http or https URL, any JSON value), and `POST /api/jobs/aircraft-report` takes `payload: { originIcao, destinationIcao, aircraftId, departureAt }`; the envelope schema is `api/endpoints/jobs/dtos/create-job.schema.ts`, and `GET`/`DELETE` work for all three queues because `jobs.queue` records the owner.

Every submission key must be a UUID; malformed keys fail HTTP validation. Every repeated submission key returns HTTP 409 with `error.details.existingJobId` (`JobConflictError` carries the ID; the optional `details` object of the error envelope is built by `api/core/response-envelope/to-error-envelope.ts` from a `details` field on the exception response), including an identical request after its scheduled time has passed; each `Create<Queue>JobUseCase` checks the existing key before schedule validation (through the private `use-case/submit-job.ts`), while the repository's advisory lock and unique key close concurrent races. `CreateAircraftReportJobUseCase` then runs the public `ValidateAircraftTransitRequestUseCase`, whose errors map to HTTP 400 (`JobsModule` imports `AircraftTransitsModule`). Instant requests omit `startAt` and are eligible immediately. All queues share one retry shape, `common/queue/retry-policy.ts` (fixed pg-boss `retryDelay`, no backoff), and each job chooses its own limit: every submission DTO takes an optional `maxAttempts` (1-10, `DEFAULT_MAX_ATTEMPTS = 4`), stored in `jobs.max_attempts` and applied as pg-boss `retryLimit = maxAttempts - 1` by `retryPolicy(maxAttempts)` on enqueue. The delay before the next attempt is 5 s after attempt 1 fails, 10 s after attempt 2, and 30 s after attempt 3 and every later one, defined once by `retryDelaySeconds(attempt)` in `retry-policy.ts`. pg-boss cannot express it (its backoff doubles with jitter), so `JobService.recordStart` passes `retryDelaySeconds(attempt)` to `writeJobTransition`, which writes it to `pgboss.job.retry_delay` in the same transaction that marks the job `processing`; when that attempt fails, however it fails (handler result, crash, expiry), pg-boss sets `start_after = now + retry_delay`. `retryPolicy` enqueues with `retryBackoff: false` and the first delay. The job is `scheduled` while it waits (effective status reads `start_after`), then `pending`. Covered by `retry-policy.spec.ts`, `job.service.spec.ts` and the failure-delay case in `api/endpoints/jobs/jobs.e2e-spec.ts`. The terminal decision reads the row, not pg-boss: `FailJobAttemptUseCase.execute(id, attempt, category, deadLetter)` returns `{ terminal }` (true when `deadLetter` or `attempt >= maxAttempts`) and handlers only map it to a settle result, because the work handler's job object carries no retry limit and a retry raises the row and the queue limit together. The submitted payload is stored on `jobs.payload` in the same transaction (pg-boss deletes finished jobs, the UI still shows them). A webhook payload takes an optional `method` (`POST` default, `PUT`), stored and ignored by the mock. On successful queued work, `jobs.result` stores `{ emailId }`, `{ webhookCallId }`, or `{ reportId }` (`CompleteJobUseCase` takes the result object) and GET returns it; synchronous email sends have no job row. Cancellation locks the pg-boss job row before checking its state and calling pg-boss cancellation, so a concurrent pickup cannot turn an active job into a cancelled one. References: `modules/jobs/`, `api/endpoints/jobs/`. These behaviors are covered by database integration tests; the unique submission key is also database enforced.

The worker logs pickup and each attempt outcome through its injected scoped `PinoLogger` using only queue name, job ID, attempt number, and outcome. Keep recipient, subject, body, webhook URL, and queue payload out of these messages. Reference: `worker/queues/email/email-job.handler.ts` and `worker/core/job-log.ts`; unit and integration tests verify the safe fields.

Worker handlers follow one shape: start the attempt, validate the payload with a Zod schema owned by the feature (an invalid payload goes straight to dead-letter with `invalid_payload`), call the feature use case, then complete the job or record a failed attempt. `webhook-job.handler.ts` treats `WebhookDeliveryFailedError` as retryable `delivery_failed` and a thrown error as `delivery_or_storage`; `aircraft-report-job.handler.ts` dead-letters unknown airport, unknown aircraft, and same-airport errors (`unknown_airport`, `unknown_aircraft`, `same_airport`) and treats thrown errors as retryable `generation_or_storage`. Side effects are keyed by job so a retry after a crash is safe: the webhook delivery key is `webhook-job:<job UUID>` and reports are unique by `job_id`. Handler specs cover each outcome; `api/endpoints/jobs/jobs-queues.e2e-spec.ts` runs a crash-before-completion retry per queue against a real database. Integration suites run serially against a prepared database (`pnpm run setup`, `pnpm db:seed`); stop other workers on the same database first because any worker consumes every queue.

For queued email delivery, keep the client submission key and provider delivery key separate. The first is unique on `jobs`; the latter is `email-job:<job UUID>` and is unique on `sent_emails`. The mock email client returns a stable receipt for that key, and the repository returns the existing sent record after a repeat. A replacement real provider must honor the same key server-side; database uniqueness alone cannot prevent a second external send after a crash. References: `modules/jobs/job.repository.ts`, `modules/emails/mock-email.client.ts`, `modules/emails/email.repository.ts`. Database uniqueness and integration tests enforce local behavior; the external provider contract is a convention.

- Package commands run from `apps/backend`; `api/core/config/config.module.ts` explicitly loads the repository root `.env` at `../../.env` so the API and database tooling share one environment file. Existing process environment values take precedence over file values. `api/core/config/api.config.ts` maps `DATABASE_URL` to `ApiConfig.postgres.url`, preserving the nested database configuration used by providers; `postgres__url` is a compatibility fallback when `DATABASE_URL` is absent. Other nested settings use double underscores. Zod enforces the parsed configuration shape at startup; environment file placement is a convention.

## Keeping this guide current

When a change implements a planned pattern or changes one of these seams, update this file in the same change: state the rule, why it exists, its reference implementation, and whether tooling enforces it. Update `/DECISIONS.md` when the choice or trade-off changes. Keep root `AGENTS.md` for cross-package rules only.
