# web

Job Queue UI: React 19 + Vite SPA. UI: Chakra UI v3 (`ChakraProvider` with `defaultSystem`, no CLI snippets). Server state: TanStack Query. Client UI state: zustand. Routing: React Router. Map: Leaflet via `react-leaflet` with OpenStreetMap tiles (free, no key).

The design source is the Claude Design project `Job Queue.dc.html` (screens 1a–1g: dashboard, jobs list, job detail, batch progress, transit report, submit, sent emails).

## Layout

- `src/app/` — providers (`app.tsx`), routes (`router.tsx`), shell (`layout.tsx`, `top-nav.tsx`)
- `src/features/<name>/` — one folder per screen area: pages, components, query hooks, store. `jobs/` owns the job contract (`job.ts`), UI rules (`job-rules.ts`), and hooks (`queries.ts`) that other features import
- `src/shared/` — cross-feature helpers (`format.ts`, `page-numbers.ts`, `api-error.ts`) and UI building blocks in `shared/ui/` (`Panel`, `PageHeader`, `Breadcrumbs`, `Pager`, `toaster`)
- `src/api/client.ts` — the only API entry point. Each function names the REST endpoint it stands for
- `src/mock/` — in-browser simulator of standalone jobs, kept with its tests but not started by the app (see below)
- Import across folders with the `@/` alias; `import/no-relative-parent-imports` forbids `../`

## Patterns

- **Real API, including batches.** Jobs, job batches (`/job-batches`), the job list, stats, airports, and the transit report come from the backend REST API (`/api`, Vite proxies it to `API_PROXY_TARGET`, default `http://localhost:3000`). The client holds no batch state, so a batch survives a full page reload (`api/client.spec.ts`). `mock/mock-server.ts` still simulates standalone jobs and keeps its tests, but nothing starts it (the batch mock and `mock/runtime.ts` are gone); remove it when its replacement is in scope. The jobs list without a type filter merges `GET /api/jobs` (standalone jobs only: the API leaves batch children out) with `GET /api/job-batches` newest first; the batch list has no filters, so `client.ts` applies status and search itself (reading all batch pages when filtered). Stats and health come from the API and count child jobs, not batch parents. Machine check: none; the merge is a convention
- **API boundary** (`src/api/`): `http.ts` is the only `fetch` and unwraps the `{ ok, data }` envelope (throws `ApiError`, which carries `existingJobId` on a repeated job key and `existingBatchId` on a repeated batch key); `schemas.ts` holds the zod schemas every response is parsed with; `mappers.ts` turns API jobs into the UI `Job` contract (activity becomes attempts and logs, queue `aircraft-report` becomes type `transit`, ICAO codes become the IATA codes the UI shows). The UI has no aircraft picker, so transit jobs use the first seeded aircraft. The sent-emails page is the job list filtered to email jobs that completed or failed, so synchronous `POST /api/emails` sends do not appear there. The Webhooks page (`features/webhooks/`) is built the same way from webhook jobs. The top nav has no Submit tab: jobs are created from the "New job" buttons (dashboard, jobs list) and the per-type buttons on the Emails and Webhooks pages, which open `/submit?type=…`
- **Demo hooks:** emails to `@bounce.test` always fail (backend email mock), to demo retries and failures on demand. The backend webhook mock fails at random (one in three); no URL forces a failure
- **Server data** goes through TanStack Query hooks (`features/jobs/queries.ts`, `features/emails/queries.ts`) that refetch every second (the design's "refreshed every second"); components never call the API client directly. Mutations invalidate `jobs`, `job`, `batch`, `batch-activity`, `health`, `emails`, `webhooks`, and `reports`
- **Filters:** the jobs list keeps its filters in the URL (`?status=&type=&q=&page=`, parsed by `jobs-filters.ts`), so views can be shared. The emails page keeps page, filters, and the expanded row in a zustand store (`emails-store.ts`) so the view survives navigation
- **Idempotency keys are generated by the UI, never typed by the user.** The submit page creates one key (a bare UUID, because the API requires one; `features/submit/idempotency-key.ts`) when the form opens, and a new one whenever a field changes or a submit succeeds. A repeated or retried submit of the same form returns the existing job instead of a duplicate (the API answers 409 with the first job's ID, and the client loads that job). Priority is 1-5, as in the API. `toSubmitInput` requires the key, so every submit sends one. Not machine-enforced beyond that signature
- **Batches hold typed tasks.** `BatchPayload` is `{ items: TaskSpec[] }`, where each task is an email, webhook, or transit report (no nested batches, 1–100 tasks; submit maps `transit` to `aircraft-report` with ICAO codes and the first aircraft, as for standalone jobs). A batch `Job` has `type: 'batch'`, the exact `batchStatus` (`scheduled`, `pending`, `processing`, `cancelling`, `cancelled`, `completed`, `completed_with_errors`), a coarse `status` for filters and counts (`COARSE_STATUS` in `job-rules.ts`: `completed_with_errors` is `failed`, `cancelling` is `processing`), `batchItems` (child statuses, including `cancelled`), and `batchChildIds`. Batch status is not a child job status: the badge shows `displayStatus(job)`. A batch has its own route, `/batches/:id` (`jobPath`), and its tasks link to `/jobs/:id`. `toUiBatch` in `api/mappers.ts` builds it; a list row has no children. The API's `progress` counts completed, failed, and cancelled children. The batch detail's Logs panel is a separate query, `useBatchActivity` (key `['batch-activity', id]`, refetched every second, invalidated with the other job queries) over `GET /api/job-batches/:id/activity`, one feed instead of up to 100 child reads; `toBatchLogs` maps it to `JobLog` lines prefixed `Task <position> · <type>:` (batch-level entries have no prefix), so `toUiBatch` still sets `logs: []`
- **Submit form** (`features/submit/`) has two panels: **Job** (type + payload fields, or the batch task list with "Add task") and **Settings** (priority, max attempts, execution). Execution is a Regular/Scheduled toggle; Scheduled shows a `datetime-local` picker with +5m/+15m/+1h quick picks. Form state is strings; `toSubmitInput` in `submit-form.ts` is the only place that validates and builds the API request
- **Payloads render as read-only forms, never JSON.** The job detail page reuses `TaskFields` without `onChange` (read-only mode) via `taskFormFromSpec`; results render as labeled fields (`result-view.tsx`). Reusing the submit fields keeps both views in step
- **IDs are shown short.** Every job, batch, and idempotency ID on screen is its first 8 characters (`shortId` in `shared/format.ts`), rendered by `ShortId` (`shared/ui/short-id.tsx`): clicking a plain ID copies the full value; an ID with `to` is a link plus a small copy button, so navigating and copying stay separate. Why: full UUIDs widen tables and add noise, and the full value is still one click away. Use `ShortId`, not raw `{job.id}`. Not machine-enforced
- **Batch task graph cells are anchors** (`#batch-task-N`) to the task definitions in `payload-view.tsx`; the target task is highlighted with the CSS `:target` state (`_target`), so no scroll or selection state lives in React
- **Grid columns use `minmax(0, …)`** so long content (URLs, text) cannot widen a column past the viewport
- **Action rules** (`canCancel`, `canRetry` in `job-rules.ts`) mirror the API: cancel only scheduled/pending jobs or a batch that is scheduled, pending, or processing (not `cancelling`); retry only failed standalone jobs; a batch child has neither (the API answers 409) and is managed through its batch. Cancelling a batch calls `DELETE /api/job-batches/:id`. Buttons for actions that are not allowed are hidden, not shown disabled. **Run again** is the exception to these rules: it is on every job detail page in any state (batch children too) and posts a new job with the same body, priority, and attempt limit, run now under a fresh idempotency key (`toRerunInput` in `job-rules.ts`, `rerun` in `use-job-actions.ts`), then opens the new job. It is a plain create, so the original keeps its history and no API change is needed
- **No escape hatches:** no `as` casts that narrow types and no lint-disable comments; use type guards or `Array.find` over constant lists instead

## Testing

- Unit-test pure logic only (`*.spec.ts` next to source, vitest, node environment): the mock server's lifecycle rules, API mappers and the API client (`fetch` stubbed: request mapping, list merge and paging, batch cancellation, reload), form parsing, filters, formatting, geo math
- No component or e2e tests for UI. Verify UI manually in a browser (Claude in Chrome MCP when available); the app needs no auth
