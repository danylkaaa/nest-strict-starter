# Plan: queued email jobs with pg-boss

## Solution approach

Use pg-boss for delayed pickup, priority, retries, claim recovery, and queue settlement. Keep a durable application `jobs` row for submission idempotency and the public six-state status, plus append-only `job_activity` rows for history. Keep HTTP adaptation in `api/`, consumers and handler registration in `worker/`, business actions in `modules/jobs/` and `modules/emails/`, and reusable pg-boss connection setup in `common/queue/`. The API and worker run as separate Nest applications against the same PostgreSQL database. The existing synchronous email endpoint stays intact.

The client submission key and delivery key serve different purposes. A unique submission key identifies one job request; a delivery key derived from its job ID identifies one email send across retries. pg-boss singleton policies are insufficient for delivery idempotency after a crash. The mock client must return the same delivery receipt for repeated calls with a delivery key, and `sent_emails` must be unique on that key. A future real provider must honor the delivery key server-side before replacing the mock.

## Ordered implementation

1. **Persist jobs, events, and delivery identity.** Add `jobs` and `job_activity` to `packages/database/src/schema.ts`, including the unique UUID client idempotency key, pg-boss UUID, type, priority, requested start time, six-state status, nullable JSON result, safe timestamps, event order, and foreign key. Add a unique delivery key to `sent_emails`; keep synchronous emails independent of jobs. Generate and review the migrations under `packages/database/migrations/`; update the package guide and `DECISIONS.md`. Keep email content out of activity rows. Verify with schema and repository tests for uniqueness, ordered events, status transitions, duplicate delivery keys, and a completed job result containing its sent email ID; run `pnpm db:generate` and `pnpm check`.

2. **Build queue wiring and a separate worker application.** Install `pg-boss` in `apps/backend`. Add a reusable connection/provider module under `src/common/queue/` that starts pg-boss with `migrate: false` to verify an already prepared schema, checks that the email queue exists, exposes a publisher, and stops cleanly on Nest shutdown. Add a `src/worker/main.ts` bootstrap, worker config/module, and a `@JobHandler` decorator with startup registration limited to worker providers. Add backend worker build/start scripts and a backend-owned pg-boss migration command that creates or upgrades the pg-boss schema and the email queue; invoke that command from root `scripts/setup.mjs` after Drizzle migrations. Document API/worker startup in `apps/backend/AGENTS.md` and the root README. Check the installed pg-boss API and types before coding the adapter. Verify provider lifecycle and decorator discovery with focused tests; run setup against a disposable database and confirm it creates the pg-boss schema and queue before API or worker startup; confirm API startup does not register consumers.

3. **Implement job commands and HTTP endpoints.** Add public `CreateEmailJobUseCase`, `GetJobUseCase`, and `CancelJobUseCase` under `src/modules/jobs/use-case/`, with a feature-owned repository port/adapter. Add `POST /api/jobs/email`, `GET /api/jobs/:id`, and `DELETE /api/jobs/:id` under `src/api/endpoints/jobs/`, with Zod DTOs and Swagger envelopes. The POST DTO requires UUID `idempotencyKey`, `priority` (integer 1–5), `type` (`instant` or `schedule`), and `payload` using the existing email Zod schema; `startAt` is required and future-dated only for `schedule`. Pass `priority` and `startAfter` to pg-boss. Use one PostgreSQL transaction for job creation, activity creation, and pg-boss `send(..., { db })`, with a preassigned job UUID; serialize concurrent requests for the same idempotency key. Return HTTP 409 Conflict for every repeated idempotency key, including an identical request; detect duplicates before applying the future-time check to an existing key. Do not hash or store the job request body. Cancel only queued/scheduled jobs, with the queue cancellation and application state/event update coordinated in a transaction. Return `jobs.result` through GET, with `{ emailId }` on successful email completion. Verify UUID key validation, DTO bounds, schedule timing, priority, 202 response, deduplication races, GET/not-found/result, and cancellation state/races with API integration tests.

4. **Process jobs, retries, and lifecycle history.** Register an email consumer in `src/worker/` using the decorator; validate queue data before invoking `SendEmailUseCase`. Extend the email client port/use case/repository so queued sends supply a separate delivery idempotency key; preserve the synchronous endpoint behavior. Configure pg-boss for three retries, a 60-second initial delay, and exponential backoff. Use the installed version's per-job terminal-failure mechanism to bypass retries for malformed queue data. Append start, failed-attempt, completed, final-failed, and cancellation activity while updating the six-state job record; store the sent email ID in `jobs.result` on success; reconcile pg-boss retry/terminal state after crashes or settlement gaps so the public status does not remain `processing`. Ensure events are inserted once per job/attempt/transition. Log pickup and each attempt outcome through the scoped worker logger with queue name, job ID, and attempt number, excluding email content and recipient. Verify successful and repeated delivery, four-attempt limit, backoff options, malformed payload terminal failure, crash recovery, final status, ordered activity, result email ID, and safe log fields with worker and database integration tests.

5. **Run and document the complete flow.** Start migrated PostgreSQL, API, and worker as separate processes; submit instant and scheduled test jobs, inspect status/activity, and cancel a pending job. Run `pnpm check` from the repository root and manually review backend dependency direction until its machine check is restored. Update `apps/backend/AGENTS.md`, `packages/database/AGENTS.md`, `DECISIONS.md`, and the startup/request examples with the implemented pattern and trade-offs. The implementation is done when all accepted facts in `facts.md` pass automated checks and the root quality gate is green.

## Risks and decisions to verify during implementation

- **Crash window and durable activity:** pg-boss settles a `work()` result after the handler returns. A process can stop between an application event write and queue settlement. Verify the chosen pg-boss version's transaction hooks or implement a reconciliation pass keyed by job ID and retry count. The public status must ultimately agree with pg-boss, and event insertion must be idempotent.
- **External delivery guarantee:** The mock can guarantee stable delivery by key. No local PostgreSQL transaction can make a future external provider call exactly once; its API must accept the separate delivery idempotency key. Test the mock behavior and document this contract.
- **Cancellation race:** pg-boss can cancel active jobs, but this API must reject them. Perform the state check and queue cancellation atomically where supported, and verify the affected-row result before recording `cancelled`.
- **Queue state mapping:** Map pg-boss created/retry to `scheduled` when the next eligible time is in the future and `pending` otherwise; active/completed/failed/cancelled map to their public equivalents. Do not assume priority preempts an already active job; it orders eligible pickup.
- **Database ownership:** pg-boss creates its own schema on startup. The app migration owns `jobs`, `job_activity`, and `sent_emails` changes. Confirm startup permissions and the shared transaction adapter against the installed pg-boss release.
