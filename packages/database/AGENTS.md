# @workspace/database

Owns the PostgreSQL schema, generated migrations, and typed Drizzle client. The API consumes compiled exports through `workspace:*`; keep schema changes here so other consumers use the same tables.

- **[convention]** Define tables in `src/schema.ts`; TypeScript properties use camelCase and SQL columns use snake_case. `sentEmails` is the reference: `eml_<ULID>` ID generated by Drizzle, unique mock message ID, and non-null recipient, subject, body, and send time. The SQL check enforces ID shape even for raw SQL inserts; raw SQL writers must supply a valid ID.
- **[enforced]** `webhookCalls` records one outcome per webhook attempt so retries retain history. Its `jobId` is a required `uuid` foreign key to `jobs`, indexed with the `whc_<ULID>` record ID for job filtering. The response fields are present only on success; error name and message are present only on failure. SQL checks enforce the ID, outcome, and result shape, and a partial unique index on `jobId` where `outcome = 'succeeded'` allows at most one success per job while keeping every failed attempt. `src/schema.ts` and migration `0000` are the references.
- **[enforced]** `airports` (uppercase four-letter `icao` primary key, coordinate range check) and `aircraft` (`acf_<ULID>` id, unique registration, positive performance check) are reference tables; `aircraftTransitReports` (`atr_<ULID>`, foreign keys to both, jsonb `waypoints`) stores generated reports. Each report has a `jobId` foreign key to `jobs` with a unique index, so one aircraft report job produces one report. `pnpm run setup` invokes `pnpm db:seed` (root Turbo task; package script `tsx src/seed.ts`) after migrations to fill the reference tables from `src/seed-data/` with `onConflictDoNothing`, so reruns are safe. It reads `DATABASE_URL` from the root `.env` like `drizzle.config.ts`. Migration `0000` is the reference.
- **[enforced]** `jobs` is the application-owned durable status and submission-idempotency record for pg-boss jobs. Its UUID is also the pg-boss job ID; the client submission key is a unique PostgreSQL UUID, and priority, six public statuses, and the `queue` (`email`, `webhook`, `aircraft-report`) have SQL checks. Every repeated submission key is an application error; no job body hash is stored. `jobs.payload` (jsonb, not null) keeps the submitted payload because pg-boss deletes finished jobs after retention; `jobs.max_attempts` (not null, `>= 1`) is the job's attempt limit (API range 1-10; a retry raises it by one, so SQL does not cap it), and `jobs_created_at_id_idx` serves the newest-first list. `jobActivity.event` includes `retried` (key `retried:<attempt>`), and terminal `failed` events are keyed `failed:<attempt>`. The nullable JSON `jobs.result` is a union, `{ emailId }`, `{ webhookCallId }`, or `{ reportId }`, written when the queued work completes; synchronous emails have no job. `jobActivity` is an append-only lifecycle log: each `(jobId, eventKey)` is unique so a retried transition cannot duplicate an event, and `jobId` references `jobs`. `sentEmails.deliveryKey` is nullable for the existing synchronous endpoint and unique for queued delivery. `src/schema.ts` and migration `0000` are the references. The migration history was regenerated from `0000` when the webhook and aircraft report queues were added (nothing was deployed); reset a development database with `docker compose down -v && pnpm run setup`. SQL enforces identity, enum/range, and event uniqueness; result shape, transition order, and duplicate-key error behavior are application rules.
- **[enforced]** `jobBatches` (`job_batches`) is the durable parent of a batch: UUID `id`, unique UUID `idempotency_key` (its own namespace; standalone job keys stay on `jobs`), shared `start_at`, nullable `cancellation_requested_at` (set once), and `created_at`. A child is an ordinary `jobs` row with nullable `batch_id` (foreign key) and `batch_position`; checks require both to be null together and the position to be nonnegative (0-based), and a unique index on `(batch_id, batch_position)` also serves the child lookup. A job belongs to at most one batch and existing jobs stay valid with both null. There is no status or progress column: batch status, counts, and progress are derived from the children at read time, and there is no parent pg-boss job because nothing needs to run for a batch. Migration `0001` is additive (new table, two nullable columns, constraints, index) and keeps `0000` and existing data. SQL enforces identity, the pairing, and position uniqueness; the 1-100 size, child type, and derived status are application rules. Reference: `src/schema.ts`, migration `0001`, `DECISIONS.md` "Persistent job batches".
- Generate migrations with root `pnpm db:generate`; review and commit SQL plus metadata under `migrations/`. Apply with root `pnpm db:migrate`. Both Turbo tasks are uncached because they change files or external state. `drizzle.config.ts` loads `DATABASE_URL` from the root `.env` so migrations and the backend use one database URL. The `pnpm run setup` script creates that URL from root PostgreSQL settings for local development; process environment takes precedence when running migration commands directly. This convention is not machine-enforced.
- Runtime exports point to `dist/`. Root Turbo tasks build dependencies before API checks, tests, and startup. After a schema change, regenerate migrations; `pnpm dev` watches both the package and API.
- Tests sit beside source. `pnpm check` checks the package and API; real database tests are separate (`apps/api` script `test:integration`) and require a migrated disposable database.
